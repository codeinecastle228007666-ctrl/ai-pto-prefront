# Переход фронтенда с моков на живой бэк

Документ описывает, какие эндпоинты вызывает фронтенд, что из них уже работает в `AI-PTO-BACK`, что осталось реализовать и где контракты расходятся. Задачи в виде чеклиста: [задачи-переход-с-моков.md](задачи-переход-с-моков.md).

Состояние на 2026-10-05, ветка `feature/document-review`.

Контракт объединён в один файл: `AI-PTO-BACK/docs/openapi.yaml`, правка закоммичена в ветке бэка `feature/openapi-contract` (создана от `feature/tsc-build`, потому что полного контракта нет в `develop`). Фронтенд и моки приведены к нему.

## Как включается мок-режим

- `VITE_USE_MOCKS=true` — запросы перехватывает MSW (`src/mocks`), бэк не нужен.
- `VITE_USE_MOCKS=false` — запросы идут на `/api`, который vite проксирует на `VITE_PROXY_TARGET` (по умолчанию `http://localhost:3000`). Cookie-сессия работает без CORS, потому что origin один.
- Для локальной работы с бэком создайте `.env.local` с `VITE_USE_MOCKS=false`. Бэк при этом запускается с `AUTH_PROVIDER=local`, пользователь создаётся `yarn user:create`.

## Экраны и эндпоинты

| Экран | Метод и путь | В бэке |
|---|---|---|
| Вход, профиль | `POST /auth/login`, `POST /auth/logout`, `GET /auth/me` | работает |
| Объекты | `GET/POST /objects`, `GET/PATCH /objects/{id}`, `POST /objects/{id}/status`, `POST /objects/{id}/archive` | работает |
| Справочники | `GET /object-types`, `GET /work-types`, `GET /counterparties` | работает |
| Загрузка | `POST /objects/{id}/packages` | заглушка |
| Загрузка | `PUT <uploadUrl>` в объектное хранилище | не реализовано |
| Загрузка | `POST /packages/{id}/start` | заглушка |
| Пакет | `GET /packages/{id}` | заглушка |
| Пакет | `GET /packages/{id}/events` (SSE) | заглушка |
| Просмотр | `GET /documents/{id}`, `GET /documents/{id}/file` | заглушка |
| Поля | `PATCH /documents/{id}/fields` | заглушка |
| Замечания | `GET /objects/{id}/findings`, `PATCH /findings/{id}` | заглушка |
| Комплект | `GET /objects/{id}/checklist` | заглушка |
| Отчёт | `POST /packages/{id}/reports`, `GET /reports/{id}`, `GET /reports/{id}/download` | заглушка |

«Заглушка» — контроллер есть, сервис бросает `NotImplementedException`.

## Что нужно реализовать на бэке

1. **Объектное хранилище.** MinIO есть в `docker-compose`, S3-клиента в зависимостях нет. Нужны presigned PUT для загрузки, presigned GET для оригинала и отчёта, проверка `sha256` для дедупликации.
2. **Пайплайн обработки.** Каталоги `pipeline/`, `rules/`, `llm/`, `parsing/` пока пусты. Этапы `extract → classify → parse → rules → explain` запускаются из `start` и работают в отдельном воркере. Очередь BullMQ требует Redis, который из зависимостей убран, это нужно решить до начала работ.
3. **Модули `packages`, `documents`, `findings`, `checklist`, `reports`.** Модели в Prisma-схеме уже описаны.
4. **SSE.** События воркера доставляются в API (pub/sub или опрос БД).
5. **Генерация PDF-отчёта** и его сохранение в хранилище.

Без пайплайна фронтенду нечего показывать: не будет ни типов документов, ни полей, ни замечаний.

## Решения по контракту

| Область | Решение |
|---|---|
| Объекты | массив без пагинации (ожидается до десятка объектов у исполнителя), единственный параметр `includeArchived`; поиск, фильтры и сортировка на клиенте |
| Справочники | `/object-types`, `/work-types`, `/counterparties` как в коде бэка |
| Роли | `owner`, `engineer`; архивирует только `owner` |
| Вход | только email и пароль; ZITADEL из документации убран, из кода его уберёт отдельная задача |
| Создание пакета | ответ `{packageId, version, uploads[{documentId, url, objectKey, duplicateOf}]}`, PUT на `url`; у дубликата `url: null` |
| Подтверждение загрузки | отдельного запроса нет, `start` проверяет, что все файлы в хранилище |
| Дедупликация по хешу | по `sha256` (необязателен) определяется `duplicateOf`: файл не загружается и не обрабатывается; `start` дубликат не ждёт и сверяет хеш остальных |
| SSE | два события: `progress` (пакет) и `document.stage` (этап документа); истина о документах — `GET /packages/{id}` |
| Пофайловая готовность | документ в статусе `done` открывается, не дожидаясь пакета: поля и замечания сразу, комплект предварительный, отчёт после обработки всех документов |
| Документы, поля, замечания, сводка | как в полном контракте |
| Комплект | `GET /objects/{id}/checklist`, считается по видам работ объекта; `packageId` необязателен |
| Отчёты | как в полном контракте, скачивание отдаёт PDF (решение принято по умолчанию, не обсуждалось) |

## Что ещё нужно выровнять на бэке

- Влить `feature/openapi-contract` (один коммит, только `docs/openapi.yaml`) вместе с `feature/tsc-build`, от которой он создан.
- Привести `src/common/dto/openapi.types.ts` к контракту: `Finding` (`sources`, `expected`, `actual`, `normRef`, `explanation`), `PackageCreated` (с `duplicateOf`), события `progress` и `document.stage`, `ExtractedField`.
- Удалить стадийный `docs/openapi/openapi.yaml` (или пометить устаревшим) и поправить ссылки на него в `docs/tasks/stage-1`.
- Отдельная задача: вырезать ZITADEL из кодовой базы (`oidc.service.ts`, `zitadel-key.ts`, `GET /auth/login`, `/auth/callback`, `AUTH_PROVIDER`, каталог `zitadel/`).

## Что проверить на стороне фронтенда при переходе

- Формы ответов реального бэка совпадают с типами в `src/entities/*`. Проверялось только по спецификации, не против сервера.
- PUT на `url` уходит с `Content-Type`, равным `mimeType` из запроса создания пакета: хранилище подписывает ссылку с этим заголовком.
- CORS бакета объектного хранилища: браузер делает PUT напрямую в MinIO/S3 (метод `PUT`, заголовок `Content-Type`, origin фронтенда).
- Прокси и SSE: нет буферизации `text/event-stream`, cookie `ai_pto_session` доходит до `/events`.
- Сценарий целиком: вход, создание объекта, загрузка, прогресс, замечания, подсветка в PDF, правка поля, отчёт.
- После успешной проверки решить судьбу моков: удалить `src/mocks/data/{packages,findings,fields,reports}.ts` и обработчики либо оставить для демо-режима.

## Порядок работ

1. Хранилище, `packages` + `start` без обработки (в моках и контракте уже учтены дубликаты). Загрузка работает на живом бэке, пакет остаётся в `queued`.
2. Воркер с `extract` и `classify`: типы документов, просмотр оригинала.
3. `parse`: вкладка «Поля».
4. `rules` и `explain`: замечания и подсветка.
5. Комплектность, SSE, отчёт.
